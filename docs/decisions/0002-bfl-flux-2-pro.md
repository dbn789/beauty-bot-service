## Сеть: доступность bfl с российских IP (расследование 2026-10-10)

Симптом: генерации через бот падали «fetch failed» / UND_ERR_CONNECT_TIMEOUT при том, что curl с той же машины работал.

Причина (подтверждена бесплатными пробами `GET /v1/credits`, 19/19 успешных):
- **блока bfl по RF-IP нет** — все эндпоинты (global/eu/us) отвечают напрямую;
- сбой давал **DNS bfl с AAAA-записью первой по ротации** в сети без IPv6-маршрута:
  fetch Node 18 не откатывается на IPv4 (в отличие от curl) → прерывистые
  CONNECT_TIMEOUT. Telegram API с локальной машины также нестабилен (частичный
  RKN-блок) — телеметрия polling дёргается рывками, но работает.

Решение в коде (apps/bot/index.js, scripts/bfl-live-check.js):
`dns.setDefaultResultOrder('ipv4first')` + `net.setDefaultAutoSelectFamily(true)`.
На node:22 (docker) autoSelectFamily включён и так — фикс страхует локальную разработку.

### План для Amvera (Э3, без трат)

1. После деплоя в Москву: бесплатная проба `/credits` из контейнера (через `scripts/bfl-live-check.js --probe`-режим или health). Если 200 — работаем напрямую, `BFL_BASE_URL` не нужен.
2. Если из Москвы bfl недоступен: прописать `BFL_BASE_URL=https://api.eu.bfl.ai/v1`; если и это не помогает — перенос проекта бота (и БД) в регион Варшава (FR-I-050, план Б): там нет ни RKN-блоков Telegram, ни возможных гео-ограничений.

Правило экономии на время приёмки: диагностика только через `GET /v1/credits` (бесплатно), генерации — только по явной команде владельца ключа.

## Последствия

- Дефолт `BFL_MODEL=flux-2-pro` уже в конфиге; цены в `packages/shared/pricing.js`.
- Бюджет-стоп: $5/день ≈ 37 генераций/день на pro — с запасом для одного салона.
- Ожидаемый UX: полный цикл ~30–45 с (таймаут 120 с с запасом; статусы и chat action уже реализованы).
- Риск: глобальный эндпоинт на Amvera (Москва) может вести себя так же, как локально — на Э3 проверить и при необходимости прописать `BFL_BASE_URL=https://api.eu.bfl.ai/v1` в переменных проекта.
